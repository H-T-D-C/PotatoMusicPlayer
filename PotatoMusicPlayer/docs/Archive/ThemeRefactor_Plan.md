# テーマ基盤の大幅改修計画

## 1. 目的

ライトモードの見落とし箇所を人が画面ごとに探し続ける運用をなくす。色やスタイルを追加・変更したとき、ライト／ダーク両テーマへの反映漏れを仕組みで検出し、テーマ間の差分を一元管理する。

この改修は、ライトモードの色を一度調整する作業ではない。WPFにテーマ切替機能を追加すれば自動的に全コントロールが適切な配色になるわけではないため、アプリ内の配色を意味ベースのテーマリソースに集約し、規約と自動検査で漏れを防ぐ。

## 2. 改修前の課題

- 設定には Light／Dark／System があり、起動時・設定変更時に `ThemeService.Apply()` が動作する。
- 配色定義は `Resources/Themes/DarkTheme.xaml` にあり、切替時は `ThemeService` がアプリケーションリソース内のブラシ色を個別に書き換える。
- XAMLやコードビハインドにも色の直書きがある。例として設定画面のスクロールバー、リセットボタン、メイン画面の背景、波形・再生ヘッド・ミニマップ、入力ダイアログがある。
- `DarkComboBoxStyle` など、ダークテーマ固有の名前が共通スタイルのように使われている。
- この構成では新しい色や描画要素を加えるたびに、開発者がライトモード未対応箇所を把握して個別対応する必要がある。

## 3. 目標と完了条件

1. アプリの見た目に関わる色は、原則としてテーマリソース経由で指定する。
2. ライト／ダークの両パレットに必要なリソースが揃っていることを自動検査する。
3. UIコードやXAMLに許可されていない色の直書きが追加された場合、自動検査で失敗させる。
4. 基本的な文字色と背景色など、意味のある色の組み合わせを機械的に検査する。
5. Light／Dark／System の既存設定値と保存済み設定を維持し、テーマ変更を画面とダイアログへ反映する。
6. 新しい画面・コントロールを加えるときに、個別のライトモード確認箇所を列挙しなくても、共通リソースの利用と検査によって未対応を検出できる。

## 4. 設計方針

### 4.1 意味ベースのテーマトークン

色名を `Dark...` や `Light...` ではなく、用途で定義する。例：

- `SurfaceWindowBrush`、`SurfacePanelBrush`、`SurfaceControlBrush`
- `TextPrimaryBrush`、`TextSecondaryBrush`、`TextDisabledBrush`
- `BorderDefaultBrush`、`BorderFocusBrush`
- `AccentBrush`、`AccentHoverBrush`、`AccentPressedBrush`
- `WaveformSurfaceBrush`、`WaveformBarBrush`、`PlaybackCursorBrush`
- `RangeOverlayBrush`、`ScrollBarThumbBrush`、`DangerHoverBrush`

実際のキーは既存画面を棚卸しして確定する。ライト／ダーク間で意味を揃え、各テーマで値だけを変える。色だけでなく、テーマで差を持たせる必要があるコントロールスタイルも共通スタイル側へ整理する。

### 4.2 リソース辞書の分割と切替

- `ThemeTokens.xaml` などに、テーマに依存しない共通スタイルを置く。
- `Resources/Themes/Light.xaml` と `Dark.xaml` に、同一キー構成のテーマ値を置く。
- 起動時に設定を読み、選択テーマの辞書を適用する。Light／Dark の手動選択はそのまま維持する。
- System は Windows のアプリテーマ設定を解決する。テーマ変更を起動中も追従させるかは実装時に対応範囲を決め、追従する場合はレジストリ通知の登録・解除も設計する。
- テーマ変更時に開いているメイン画面・設定画面・入力ダイアログにも反映されるよう、動的リソース参照を基本にする。
- 起動時の白い瞬間表示は別のWPF初期描画課題として扱い、テーマ設計だけで解決したとみなさない。

WPF自体に、アプリ固有のすべてのコントロールとCanvas描画を自動でライト／ダーク対応させる一括切替機能がある前提にはしない。リソース辞書切替を配色の仕組みとして採用し、独自描画も同じトークンを使う。

### 4.3 配色直書きの制御

- アプリUIのXAML/C#での色リテラル、`Brushes.White` 等の固定ブラシ、テーマ判定による個別色分岐を原則禁止する。
- アイコンの固定色など例外が必要な場合は、対象を狭くした許可リストと理由を検査設定に記録する。
- `SystemColors` のようなOS標準色を使う場合も、意図したOS追従として許可対象を明示する。
- 色値はテーマ辞書にのみ置く。アプリ内UIの追加時は意味に合う既存トークンを使い、新規トークンが必要なら両テーマに追加する。

## 5. 実装状況

- Light／Dark 配色辞書と共通 `ThemeStyles.xaml` を分離した。
- `ThemeService` を辞書切替方式に変更し、System 選択時は Windows のテーマ変更に追従する。
- メイン画面、設定画面、入力ダイアログ、波形、ミニマップの色をテーマリソースへ移行した。
- ビルド時ガードでテーマキー一致、XAML/C#のリソース参照、主要なコントラスト比、UI色直書きを検査する。
- Windows向けビルドは成功。実ウィンドウでのライト／ダーク表示確認は未実施。

## 6. 自動検査の計画

新たなテストプロジェクトまたはビルド時検査スクリプトを追加し、少なくとも次を検査する。既存ガイドに自動テストプロジェクトがないため、導入方法とCI／ローカルでの実行経路もこの改修に含める。

1. **テーマキー網羅性**：Light と Dark のリソース辞書が同じ必須キーを持ち、値が未定義・nullでない。
2. **UI色直書き検出**：対象のXAML/C#でカラーコード、固定色ブラシ、テーマ別個別分岐を検出する。許可リスト以外は失敗とする。
3. **コントラスト検査**：本文／補助／無効文字、フォーカス表示など、定義した意味上の組み合わせをLight／Dark双方で計算し、最低基準を満たす。
4. **テーマ解決検査**：Light／Dark／Systemの選択から正しい辞書が選ばれ、既存設定値の読み書き形式が変わらないことを検査する。
5. **動的参照の規約検査**：実行時に変わりうるテーマリソースを静的参照で固定していないかを検査する。例外は理由付きで記録する。

これにより「漏れを人が探す」代わりに「漏れを追加した変更を機械が拒否する」運用を目指す。検査は規約外の新規色や未定義トークンを高い確率で捕まえるが、コントラストの選定自体が適切か、標準ダイアログなどアプリ管理外の見た目まで完全保証するものではない。画面全体を毎回手動走査する運用は完了条件にしない。

## 7. 実装フェーズ

### Phase 1：配色の棚卸しとトークン表

- XAML、コードビハインド、動的生成UIを調べ、色・スタイル・描画要素の用途を一覧化する。
- 現在のダーク／ライト色を基に意味ベースのトークン表を作る。
- 対象外（Windows標準ファイル選択など）と許可する固定色を定義する。

### Phase 2：リソース切替基盤

- 共通スタイル、Lightパレット、Darkパレットを分割する。
- `ThemeService` を色書き換え処理からテーマ辞書選択処理へ変更する。
- System解決、保存済み設定との互換性、起動時適用、変更通知を維持する。

### Phase 3：UI参照の移行

- メイン画面、設定画面、メニュー、入力ダイアログ、スクロールバーをトークン参照にする。
- 波形バー、再生カーソル、ミニマップ背景・波形・範囲オーバーレイもトークンから生成する。
- `DarkComboBoxStyle` 等のテーマ固有名を汎用名に変更する。
- 記録済みのライトモード未対応色を、個別例外ではなく両パレットの値として整える。

### Phase 4：自動ガード追加

- テーマキー網羅性、色直書き、コントラスト、テーマ解決の検査を実装する。
- ビルドまたはCIで確実に実行できるようにし、失敗箇所をファイル・キー単位で示す。
- 例外許可リストは最小化し、理由を記録する。

### Phase 5：移行確認と仕様反映

- 初回移行時にのみ、ライト／ダークの主要画面、波形、ミニマップ、設定、入力ダイアログを目視確認してトークン設計の誤りを直す。
- 自動検査を通し、既存設定で各テーマが選択できることを確認する。
- 完了後はテーマ色追加のたびに画面全体を手動チェックするのではなく、自動検査を必須ゲートとする。新しいUI種類や描画方式を導入した場合は、検査対象に加える。
- `PotatoMusicPlayer_Specification.md` のテーマ設計・検証方針を更新し、波形仕様書のライトモード未対応メモを解消済み項目へ整理する。

## 8. 対象外・別課題

- アプリ起動、設定画面、Windows標準ファイル選択ダイアログの初回白表示は、既知のWPF／Windows初期描画課題として別管理する。
- 設定画面の数値欄・リセットボタンのレイアウト崩れ、最小ウィンドウでの操作部品の隠れは、配色とは別のUIレイアウト修正として扱う。ただしテーマ移行確認時に再発・顕在化したものは記録する。
- 波形ズームや再生同期の不具合修正は対象外。
- 将来の新しいテーマ（高コントラスト等）は、トークン構造を拡張すれば追加できる設計を目指すが、今回の実装対象はLight／Dark／Systemとする。

## 9. リスクと判断事項

- 色の直書き検出は、許可範囲が広すぎると目的を損なう。初期導入時に既存例外を精査し、追加時は理由を必須にする。
- コントラスト計算だけでは色の意味や波形の視認性を保証できない。トークンの意味と対象ペアを明示し、初回移行時の目視確認で基準を調整する。
- Canvas上の動的描画やコード生成UIはXAML検査だけでは検出できない。色リテラル検出をC#にも適用し、テーマトークン参照を標準経路にする。
- Systemテーマの実行中追従は、現在の仕様書では明確でない。今回の改修で起動時のみか即時追従かを決定し、仕様書へ記録する。

## 10. 計画上の結論

テーマリソースの整理だけでは、ライトモードの手動全件チェックはなくならない。意味ベースの共通トークンに加えて、色直書き禁止の自動検査、テーマ間のキー網羅性、コントラスト検査を導入することで、未対応箇所の追加を人が目視で探す作業から、変更時に自動で検出する仕組みへ移す。
